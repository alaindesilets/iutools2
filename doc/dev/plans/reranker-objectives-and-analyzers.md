# Decomposition re-ranking: objectives, analyzers, and the case for
# multiple re-rankers

Both morphological analyzers in this project return a *list* of candidate
decompositions per word, in some order. 

The decomps in those lists are not equally good.

- In principle, all decomps produced by R2L (Benoit's Uqailaut) are grammatically correct. But that does not mean they are idomatic, i.e. that they are likely to correpond to a common usage. 
- The FST only ever produces decomps that fit *its own* coded grammar (barring a bug). But that coded grammar is a loose approximation of the language's, so at the time of this writing it still produces lots of decomps that are not grammatical Inuktitut. And, like for R2L, some of its grammatical decomps may not correspond to an idiomatic use.

For that purpose, we have trained several re-rankers, whose aims are to bring the most grammatically correct and/or idiomatic decomps to the top.

This document provides details on the following.

1. the distinct objectives a re-ranker can optimise, and why they conflict;
2. the best numbers obtained so far, per analyzer × objective;
3. the discussion (2026-09-06) about having **different re-rankers for
   different uses and different analyzers**, and the recommendation that
   came out of it.

Short story, it's hard to develop a single re-ranker that will optimise all 
plausible metrics for all decomposers. Therefore, it might make more sense to 
have several re-rankers, and we pick the one based on the use case and the 
specific analyser userd.

The blow-by-blow experiment log for the FST
re-ranker is `data/grammar/fst/reranker-experiment.md`; the feature set,
CV machinery, and GBDT internals live in `data/grammar/fst/reranker_*.py`.

Nothing here is wired into `:core`, `:cli`, or a shipped analyzer. The
re-ranker is still an offline experiment (stdlib `.py` + a feature table).

## 1. The objectives

All measured on the **917 "fair" words** of the Hansard gold standard
(`data/grammar/gold-standard/gold-standard.csv`, `source=hansard`, minus
misspelled / possibly-misspelled / borrowed / proper-name / decomp-unknown
cases -- the same population as the `:cli` accuracy suite). The re-ranker
feature table additionally drops words where the analyzer never produces
the reference decomp at all (~38 words for the FST -- "unrankable").

Two gold columns drive the metrics:

- **`decomp_as_found_in_source`** -- the single Hansard-attested reading,
  human-curated. This is the "reference" decomp.
- **`all_correct_decomps`** -- every decomposition R2L itself can produce
  for the word (a broader "grammatically plausible" set). **Generated by
  running R2L**, so any metric scored against it is capped at "R2L parity"
  and is circular against R2L or against a feature that encodes R2L output.

`is_correct` (in the feature table) = candidate matches the reference decomp
**OR** appears in `all_correct_decomps` (union).

| metric | definition | what it is for | caveat |
|---|---|---|---|
| **reference@1** | top decomp == the Hansard reference | "show the one reading the word actually has in running text"; feeds Guess Meaning; the `:cli` gate metric | needs corpus attestation; the hard, valuable one |
| **correct@1** | top decomp ∈ `is_correct` (any grammatical reading) | "show *a* well-formed analysis, not garbage" | circular vs R2L (100% for R2L by construction); FST-config-vs-config only |
| **R-precision** | of the word's R correct decomps, fraction in the top R by score | "cluster the whole correct set at the top" | scored against `is_correct` → R2L-parity-capped |
| **P@min(5,N)** | of the top min(5, N) by score (N = list length), fraction correct | "what a user who sees ~5 decomps actually gets" | same; also bounded by R (see §5) |

### Why reference@1 and the "cluster all correct" objectives conflict

If every correct decomp is treated as equally good (train target
`is_correct` or the 3-tier `graded`), the model loses the signal that
distinguishes the Hansard reading from its grammatical siblings, and
reference@1 collapses. Measured, FST GBDT, deployable (no r2l feature):
`reference` target 91.6% reference@1 → `graded` target 79.5% (−12 pts) for
+5.8 R-precision / +3.7 P@min(5,N). A bad trade unless the product stops
privileging the corpus-attested reading.

## 2. The analyzers

### R2L / Uqailaut (`:core` `MorphologicalAnalyzer_R2L.decomposeWord()`)

The single source of truth. What the app runs today. Its output order **is**
the shared 5-key sort (`MorphologicalAnalyzer.sortDecompositions` ==
`data/grammar/fst/benoit_sort.sort_with_frequency_tiebreak`).

- reference present *somewhere* in its list: **917/919 (99.8%)**
- reference@1: **73.2% (673/919)** -- this is the CLAUDE.md headline accuracy
- correct@1, R-precision, precision, recall: **100% by construction**
  (`all_correct_decomps` *is* R2L's output).

**So for R2L the objective collapses to one: reference@1.** The "cluster all
correct near the top" problem does not exist -- every candidate R2L emits is
in the correct set. The only useful thing a re-ranker can do for R2L is
push the reference decomp to rank 0 (73.2% → ?).

### FST (`data/grammar/fst/`, HFST-based, prototype)

Merged to `main` 2026-08-22, behind no toggle yet. Over-generates: median
6 candidates/word, mean 20, max 856 (vs R2L's small, clean lists). Needs
lenient mode + speculative lexicon entries to get coverage. Unlike R2L, a
good share of what it emits is not a valid analysis of the word at all
(wrong segmentation, or a real morpheme used in a way the language does not
actually allow). So the FST re-ranker has **both** jobs: pick the reference
first, *and* keep the list's top from being padded with wrong decomps.

## 3. Best models so far

### Measurement notes

- **Flat 10-fold CV**: one loop, model weights held out per fold, but
  hyperparameters (depth, trees, buckets, L2) chosen by a human sweep over
  the same 917 words → mild optimism (hyperparameter overfitting +
  winner's-curse over ~15 sweep configs).
- **Nested CV**: outer 10-fold (the real test) with an inner 3-fold on each
  outer-train set picking hyperparameters from a small grid; outer test
  fold influences no decision. The honest number. ~0.7 pt below flat.
- Both still assume deployment words come from the **same distribution**
  (fair Hansard, reference already in the candidate list). Arbitrary user
  input / gov.nu.ca text / OOV is an untested distribution shift -- a
  bigger unknown than the flat/nested gap.
- `* = circular` (scored against an R2L-derived label with an R2L-derived
  feature in the model).

### FST re-ranker -- flat 10-fold CV, fair (917 words)

| model | train target | r2l feat | reference@1 | correct@1 | R-prec | P@min(5,N) |
|---|---|---|---|---|---|---|
| hand sort (= R2L order) | -- | -- | 73.7 | 96.4 | 81.4 | 72.4 |
| **GBDT** | **reference** | **no** | **91.6** | **99.3** | **84.4** | **72.2** |
| GBDT | graded | no | 79.5 | 98.0 | 90.2 | 75.9 |
| GBDT | is_correct | no | 74.3 | -- | 89.7 | 76.4 |
| GBDT | reference | yes | 90.1 | -- | 91.6 | 77.6 |
| GBDT | graded | yes | 90.3 | 100* | 100* | 81.1 |
| GBDT | is_correct | yes | 61.1 | -- | 100* | 81.1 |
| linear (bucketed) | reference | yes | 81.9 | 99.5 | 94.2 | 79.4 |
| linear (bucketed) | graded | yes | 78.6 | -- | 100* | 81.1 |
| linear | reference | no | -- | -- | 86.0 | 73.6 |

### FST re-ranker -- nested CV (the honest numbers), deployable (no r2l)

| model | reference@1 | R-prec | P@min(5,N) | P@3 | MRR |
|---|---|---|---|---|---|
| hand sort | 73.2 (73.7 on the current 917-word table) | 81.4 | 72.4 | 84.6 | 0.81 |
| bucketed linear | ~86 | 84.2 | 71.8 | ~97.5 | ~0.92 |
| **GBDT** (depth 4, ~150-200 trees, lr 0.1) | **90.6 (3-seed mean; 90.0-91.2)** | 84.7 | 72.1 | ~98.5 | ~0.945 |

GBDT config: `trees` 150-200, `depth` 4, `lr` 0.1, `leaf` 20, `lambda` 1.0,
`bins` 32, `rowsub` 0.4, `featsub` 0.6, negatives subsampled ~8/positive.
Pure stdlib histogram GBDT (`reranker_gbdt.py`) -- no LightGBM (no pip in
the devcontainer).

### R2L re-ranker -- built (offline), 2026-09-08

Retargets the same feature extraction + models onto R2L's own candidate
lists. `data/grammar/fst/build_reranker_table_r2l.py` builds the table from
`hansard-cache/top10k_words_benoit_decomps.jsonl` (R2L over the top-10k
Hansard types -- covers all 917 rankable fair gold words, no live `:cli`
run); candidates are deduped to (canonical, id) sequences at their earliest
native rank; every other script runs unchanged via
`RERANKER_TABLE=scratchpad/reranker_table_r2l.jsonl`.

Table: 12 101 rows / 919 words (917 fair); 97 gold words absent from the
10k cache and 37 where R2L never produces the reference decomp are dropped.
`correct@1` / `R-precision` / `P@min(5,N)` are all ~99.9% for every config
(hand sort included) -- as §2 predicts, **for R2L the only live objective
is reference@1.**

| model | train target | reference@1 (fair) | P@3 | MRR |
|---|---|---|---|---|
| R2L native order (hand sort) | -- | 73.1 (670/917) | 85.8 | 0.808 |
| linear pairwise-logistic, all features, `--loo` | reference | 81.8 (750/917) | 97.8 | 0.898 |
| linear + quantile bucketing (`--buckets 10 --loo`) | reference | 87.7 (804/917) | 98.3 | 0.930 |
| **GBDT, nested CV, 3 seeds (20260902 / 7 / 101)** | **reference** | **90.6 / 90.8 / 91.1 (mean 90.8)** | ~98.9 | ~0.948 |

**Net: +17.5 points / ~+161 words over R2L parity** -- the same ~90%
plateau the FST re-ranker hit, slightly higher and tighter on R2L's
shorter, all-valid lists. Every outer fold's inner CV picks tree depth 4.

Error analysis (`reranker_gbdt_errors.py` on the R2L table, flat CV, 86
misses): 77% are rank-2 near-misses, 88% land in the top 3, only 10 words
(1.1%) fall outside the top 3. 3% miss rate on words the hand sort also
gets right vs 28% on words it gets wrong; 18 GBDT-only regressions against
179 recoveries. The residual wrong pick is systematically closer to the
surface string (`edit_dist` −0.44) and shorter (`n_morphemes` −0.35) than
the correct parse -- the same surface-literalness bias the FST re-ranker
showed, i.e. the ~15-word genuinely context-ambiguous core that needs
sentence context, not more features.

Not frozen to Kotlin yet, not wired into `:core` / `:cli` / the shipped
analyzer.

## 4. The multiple-re-rankers discussion (2026-09-06)

### 4a. Different re-rankers per use case?

Two distinct product needs:

| need | metric | example screen |
|---|---|---|
| one decomp shown prominently | reference@1 | Guess Meaning, main analysis display, LLM input |
| exploratory list of possible analyses | R-precision / P@min(5,N) | Morpheme Dictionary multi-decomp view |

**But `correct@1` is ~96-99% for *every* config, hand sort included (96.4%).**
The top decomp is almost always grammatically valid; reference@1's "misses"
are ~96% valid alternative readings, not garbage. So "show any valid decomp
first" is **already solved** -- it does not need its own model. That
collapses three apparent needs to two:

1. **reference decomp first** -- the re-ranker earns its keep here
   (+18 pts over the hand sort). Use the `reference` train target.
2. **any valid decomp first** -- already solved (hand sort 96.4%,
   `reference` re-ranker 99.3%). No dedicated model.
3. **top-5 clustering** -- the only case that would justify a second model
   (`graded` target: R-prec 81→90, P@min5 72→76). But the FST
   over-generation ceiling (§5) is the bigger lever there.

### 4b. Different re-rankers per analyzer?

Yes -- for R2L the objective is unambiguously reference@1 (correct@1 /
R-precision are already 100% by construction), so an R2L re-ranker has one
job and no dual-objective complexity. And R2L is the analyzer that ships,
so improving its 73.2% reference@1 is the highest-value re-ranker work
available -- higher than polishing the FST re-ranker, which improves a
prototype.

### 4c. One shared re-ranker, or two trained separately?

The features are ~90% analyzer-agnostic (morpheme count, edit distance,
category codes, frequency/bigram priors). But the candidate *distributions*
differ sharply (FST over-generates; R2L lists are short and all-valid). A
model trained on the union would be suboptimal for each. **Two models,
shared code** -- retarget `build_reranker_table.py` at R2L candidate lists,
reuse everything else.

### 4d. The r2l feature and deployability

The `r2l` feature group ("does R2L also produce this candidate, at what
rank") adds only +0.3-0.7 pt to FST reference@1 in nested CV -- not worth
running Uqailaut for, **if the FST is meant to stand alone**. But this app
already runs R2L (`:core`), so the feature is not a deployment blocker
*inside the app* -- only for a hypothetical FST-only standalone. Its big
effect is on the R2L-parity metrics (R-precision, P@min5), where it is
partly circular. On an unseen word, "R2L also produced this" is a genuine
signal; the circularity inflates the offline CV number, not necessarily
production behaviour.

### 4e. Recommendation

- **Ship one model first: the FST `reference` GBDT** (or, better, build the
  **R2L `reference` re-ranker** and ship that -- higher value, R2L is the
  mainline path). Freeze it as a Kotlin re-ranker; give it a committed
  per-word snapshot + regression check like the accuracy suite has.
- **Do not ship a second (`graded`) model now.** Add it only when a
  concrete screen (Morpheme Dictionary multi-decomp list) needs top-5
  clustering, and first check whether FST-precision work has closed the gap.
  It is a config flag away (`--target graded`), not an architecture change.
- If a second model is ever justified, measure **GBDT + r2l + `graded`
  inside the app** seriously -- it hit 90.3 reference@1 *and* 81.1 P@min5
  (the P@min5 oracle ceiling) in flat CV; the app can afford the r2l
  feature.

## 5. Why P@min(5,N) is stuck (it is not a ranking problem)

Best deployable model: **72.2%**. Decomposition of the gap:

```
72.2  measured (GBDT reference, no r2l)
81.1  oracle: perfect ranking, current FST generation   <- ranking gap  8.9 pts
100   perfect ranking AND FST emits only valid decomps  <- generation gap 18.9 pts
```

The **FST-generation gap (18.9 pts) is more than twice the ranking gap
(8.9 pts)**. P@min(5,N)'s denominator is `min(5, N)` where N = list length;
when the FST pads a list with invalid decomps, correct answers get crowded
out of the top-5 no matter how good the ranking is.

- N per word: median 6, mean 20.2, max 856. R (correct) per word: median 3,
  mean 7.8, max 168.
- 333 words (36%) have N < 5 → their P@min(5,N) can reach 100%.
- 326 words (36%) have R < min(5, N) → cannot fill their slots with correct
  decomps; e.g. 69 words with N ≥ 5 but only 1 correct decomp cap at 20%.
- The 584 words with N ≥ 5 carry 13.1 of the 18.9 generation-gap points.

**The biggest P@min(5,N) lever is FST precision (fewer invalid decomps),
not the re-ranker.** Constrained by the never-drop-coverage rule (see
`data/grammar/fst/gold-standard-fitting.md` and the FST gold-fitting
cleanup work): tightening the FST to cut wrong analyses must not also cut
the correct decomp for other words -- the classic precision/recall tension
of a morphological analyzer.

## 6. Open directions

| direction | targets | needs | status |
|---|---|---|---|
| **R2L `reference` re-ranker** | R2L reference@1 73→~90 | retarget the table builder at R2L lists; train | **done (offline) 2026-09-08: 90.8% nested, 3-seed** (§3); not frozen to Kotlin |
| **freeze a `reference` re-ranker in Kotlin** | ship the ~90% GBDT (R2L first -- it is the mainline path) into `:core` | Kotlin port of the GBDT + a committed per-word snapshot/gate | not started |
| **LLM silver standard** (sentence context) | break the ~90% reference@1 plateau on *both* analyzers | crawl bilingual sentence pairs (non-datacenter IP); LLM ranking calls; `:cli --rank-decomps` subcommand | decided direction, Gate 1 (300-400 gold words) not run; see `gov-nu-ca-crawling-investigation.md` |
| **gov.nu.ca correct-set silver standard** | FST over-generation diagnostic at scale; cross-domain `correct@1` validation | gov.nu.ca word-frequency list (Cloudflare-blocked from container); run R2L over 10k new words | discussed 2026-09-06; **cannot help reference@1** (no attestation) -- only the correct-set objectives and FST precision |
| **FST precision work** | P@min(5,N) FST 72→toward 81 | lexicon / morphotactics tightening under the never-drop-coverage rule | ongoing (FST gold-fitting cleanup) |

The ~90% reference@1 plateau is the same for both analyzers and the same
cause: corpus frequency is an imperfect proxy for "which reading is meant
in *this* sentence". The re-ranker error analysis found words with
identical shape features differing only in `freq_sum` -- genuinely
context-ambiguous. Breaking past ~90% needs sentence context, i.e. the LLM
silver standard.

## 7. Implementation state of the scripts

In `data/grammar/fst/` (uncommitted as of 2026-09-06):

- `build_reranker_table.py` -- emits `is_correct` per candidate row
  (regenerate `scratchpad/reranker_table.jsonl` after editing).
- `reranker_cv.py` -- `graded_metrics_eval()` returns
  `(R-precision, P@min(5,N), correct@1, scored)`. `relevance(r, target)`
  helper. `--target reference|correct|graded` (reference = only the
  reference decomp is positive; correct = any `is_correct` positive; graded
  = 3-tier reference > other-correct > incorrect pairwise). Every run
  prints all four metrics for both the model and the hand-sort baseline.
- `reranker_gbdt.py` -- same `--target`; `train_gbdt` builds tiered
  (higher-rel, lower-rel) group pairs.
- `reranker_nested_cv.py`, `reranker_gbdt_nested.py` -- the four metrics
  added to per-fold aggregation (model + hand baseline).

Training routines were left driven by the binary reference `label` until
the 2026-09-06 request to try retraining; `--target` is the switch. No
`:core` / Kotlin code was touched, so the `:cli:test` gate does not apply
to these changes.
