# Gold standard export (`data/grammar/gold-standard/`)

**Status: transitional.** This directory currently holds a CSV *export* of
the gold standard, generated from the Kotlin files that used to be the sole
source of truth -- so this README is written around that extraction, not
around the gold standard as a concept. Once the CSV is the only thing
anyone edits directly, rewrite this README to describe what the gold
standard *is* -- the concept, its schema, how "correct" is defined --
rather than how it currently gets produced from Kotlin.

A CSV export of the morphological analyzer's gold standard -- the
human-verified set of correct decomposition(s) per Inuktitut word, used to
score analyzer accuracy against real Hansard usage.

**The Kotlin file `OBSOLETE_MorphAnalGoldStandard_Hansard.kt` and
`MorphAnalGoldStandard_WordsThatFailedBefore.kt` are where the hand-authored
columns (decomp, flags, comments) still originate.** `gold-standard.csv` is
generated from them by `export_gold_standard.py`. Regenerate after editing
either Kotlin file:

```
python3 data/grammar/gold-standard/export_gold_standard.py
```

The `all_correct_decomps` column (see below) is regenerated separately,
since it comes from actually running the R2L analyzer, not from the Kotlin
files -- run this **after** `export_gold_standard.py`, since that script
doesn't know about the column and would otherwise leave the CSV without it:

```
./gradlew :cli:installDist   # if cli/build/install/cli/bin/cli isn't built yet
python3 data/grammar/gold-standard/add_all_correct_decomps.py
```

**Both the `:cli` Kotlin test suite and the `data/grammar/fst/` Python
tooling now read this CSV**, not the Kotlin files directly:
`MorphologicalAnalyzer_R2L__AccuracyTest`/`MorphologicalAnalyzerTest` via
`GoldStandardCsvReader.kt`, `data/grammar/fst/affix_frequency.py` and
`histogram.py` via `gold_standard_csv_reader.py`. The FST accuracy test
(`MorphologicalAnalyzer_FST__AccuracyTest`) still reads the addCase()-built
`OBSOLETE_MorphAnalGoldStandard_Hansard` directly, not yet switched over.

## Columns

| column | meaning |
|---|---|
| `source` | which gold file the row came from: `hansard` or `words_that_failed_before` |
| `word` | the Inuktitut surface word |
| `decomp_as_found_in_source` | A word may have several grammatically correct decompositions, but usually only one corresponds to the word as actually found in the source (usually Hansard). This column captures that one decomposition, in Benoit Farley's `{surface:canonical/id}...` notation; empty if the Kotlin source declared `null` (no correct decomposition, e.g. an unanalyzable proper name -- see `has_no_correct_decomp` to distinguish that from a genuinely empty-string decomp). |
| `has_no_correct_decomp` | `True` when the Kotlin source declared `null` for this word (no correct decomposition exists) -- distinguishes that case from a word whose one accepted decomposition happens to be the empty string. |
| `all_correct_decomps` | Every decomposition R2L itself produces for this word (`;`-separated), populated only for "fair" Hansard words (see the flag columns below) -- generated by `add_all_correct_decomps.py`, not hand-authored. Much broader than `decomp_as_found_in_source`: R2L explores every grammatically valid parse it can find, most of which are plausible alternate readings never attested in this particular Hansard occurrence. Empty for flagged words and for `words_that_failed_before` rows. |
| `is_misspelled` | the word is misspelled |
| `is_possibly_misspelled` | the word might be misspelled (unconfirmed) |
| `is_borrowed` | the word is borrowed from another language (typically English) |
| `decomp_unknown` | a word for which the correct decomposition could not be determined |
| `is_proper_name` | the word is a proper name |
| `comments` | free-text comment from `AnalyzerCase.caseComment`, if any |

A word with any of the five flag columns set is excluded from the "fair"
accuracy population (see `skipCase()` in `MorphologicalAnalyzer__AccuracyTest.kt`
/ `_is_flagged()` in `gold_standard_csv_reader.py`).

One row per `(word, decomp_as_found_in_source)` pair: a word with N correct
decompositions (e.g. `atuliqujaujuq`, two valid root-homograph readings)
gets N rows; `has_no_correct_decomp`, `all_correct_decomps`, the flag
columns and `comments` are repeated identically on every row for that word.

## Known data-loss quirk, reproduced as-is

`MorphAnalGoldStandardAbstract` stores cases in a `Map<String, AnalyzerCase>`
keyed by word. If a word is passed to `addCase()` twice instead of once with
both decompositions in a single `arrayOf(...)`, the second call silently
overwrites the first -- the accuracy tests never see the discarded
decomposition. This exporter reproduces that overwrite exactly, so the CSV
matches what the tests actually evaluate today, rather than silently fixing
the gold standard's content during a format migration. Three words are
affected (`amittuq`, `anginngittut`, `iqaluit`); Benoit Farley has been
asked which decomposition should be kept for each. Once he answers, the
Kotlin source and this export will both be updated to match.

## Known gaps between `decomp_as_found_in_source` and `all_correct_decomps`

For two fair words, R2L currently produces no decomposition matching the
Hansard-attested one at all (the same two words
`MorphAnalCurrentExpectations_Hansard.kt` tracks as `CORRECT_NOT_PRESENT`):

- `imaimmat` -- Benoit's own comment on this word already explains why: the
  root form `ima` isn't in the database yet.
- `taaksumunga` -- its `decomp_as_found_in_source` is itself malformed
  (`"taaksumunga taaksumunga {taaksu:taangna/rpd-ml-s}{munga:munga/tpd-dat-s}"`,
  with a stray duplicated-word prefix before the real `{...}` notation),
  copied verbatim from the Kotlin source -- not a CSV export bug.

`GoldStandardCsvAllCorrectDecompsTest.kt` / `test_gold_standard_csv_reader.py`
assert these two are the *only* such gaps; either script failing on this
check means the gap set has changed and needs investigating.
