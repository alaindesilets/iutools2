# Dev Guidelines

This doc says when project tooling should be written in Python versus
Kotlin, and how work should hand off between the two, so a capability
doesn't quietly end up with two maintained implementations that can drift
apart.

The project ships as Kotlin/JVM (`:core`, `:fst`, `:cli`, `:composeApp`),
but a lot of the linguistic-data and machine-learning work behind it — the
re-ranker experiments, corpus analysis, gold-standard tooling — was built
in Python, under `data/grammar/fst/` and `data/lexicon/`, because that
kind of exploratory, throwaway-friendly iteration is what Python is good
at and Kotlin/JVM's build-and-run cycle is not. Left unmanaged, that split
invites the two languages to quietly grow two copies of the same logic.
This doc is the rule for avoiding that.

## Python is for exploration, under `data/` only

A Python script belongs under `data/` (`data/grammar/fst/`,
`data/lexicon/...`) and nowhere else. It is for one-off analysis, corpus
mining, and validating an idea before committing to it — producing or
transforming *data* (CSV, JSONL, a trained model's parameters), not
running as part of the shipped product. It is not expected to be
maintained forever, or kept in sync with anything in Kotlin.

No pip, no sudo, in the devcontainer — this is a real, standing
constraint, not a style preference. Python code under `data/grammar/fst/`
is written pure-stdlib for exactly this reason (e.g. `reranker_gbdt.py`,
a hand-rolled histogram GBDT, because LightGBM isn't installable there).
Budget for that when choosing an approach — it explains why some of this
code looks hand-built rather than reaching for a library.

## Kotlin is what ships

`:core` / `:fst` / `:cli` / `:composeApp` are the single source of truth
for any logic that runs in the product — on a phone, on desktop, or in the
CLI a human or another tool invokes directly. Never re-implement, in
Python, logic that Kotlin also has to run. `:core` in particular is
already the project's standing rule for the analyzer itself (see
AGENTS.md); this extends the same rule to everything else that ships.

## When a Python idea matures: hand off, don't duplicate

Once a Python spike has validated an approach and it needs to become part
of what the project actually runs, there are two ways to hand it off —
which one depends on *who* needs the result, not on flipping a coin:

### (a) Full port — when the app itself needs it

The capability has to run inside the shipped app (mobile/desktop), where
there's no JVM CLI to shell out to. Port it into Kotlin once, with its own
tests, and — following this project's established pattern for anything
gold-standard-adjacent — a committed snapshot and a regression gate, the
same way the FST re-ranker and the R2L accuracy suite are guarded. The
Python original is then either retired or kept only as documented
provenance ("this Python script is what the Kotlin port was validated
against"), never as a second thing anyone has to keep passing.

### (b) Port + expose via `:cli --pipeline` — when Python scripts still need it

Some capabilities matter to the project's *research* tooling more than to
the shipped app — a re-ranking model, a scoring pass, anything a Python
analysis script wants to call repeatedly. Porting it into Kotlin still
gives one canonical implementation, but rather than Python re-deriving the
same logic, expose it through `:cli`'s `--pipeline` mode. Python then calls
it as a subprocess. This is already the shape of a pattern this project
uses without having named it: Python scripts under `data/grammar/fst/`
don't re-run R2L themselves — they read decompositions pre-generated by a
JVM CLI run (`hansard-cache/top10k_words_benoit_decomps.jsonl`).
`--pipeline` generalises that from "a cache generated once" to "callable
on demand."

**`--pipeline` should end up as one mode of the CLI as a whole, not a
per-subcommand flag** — not yet the case today. As of this writing `:cli`
implements a single command (`Main.kt`, reproducing the original iutools
CLI's `segment_iu`; its `SubCommand` multi-command framework was
deliberately not ported — see that file's header comment), with `--word` /
`--define` / `--interactive` / `--pipeline` as modes of it, and
`--pipeline` itself only decomposes words (see `pipelineJson()`). As more
capabilities get added as subcommands (a rank-decomps command, a
Hansard-example lookup, a Guess Meaning command, ...), they should **not**
each grow their own private `--pipeline` mode. There should be exactly one
`--pipeline` entry point for the whole `:cli` binary: one long-running
process, reading requests from stdin that each name which subcommand to
run, dispatched internally — so a Python script orchestrating several
steps (decompose, then look up Hansard examples) keeps one subprocess and
one JVM start-up for the whole workflow, instead of spawning a process per
subcommand. `doc/dev/plans/cli-subcommands.md` is the (not-yet-started)
design for the subcommand dispatcher this depends on; a prior attempt at
a JSON-request `--pipeline` dispatcher (`PipelineDispatcher.kt`) was
built and then reverted during the 2026-09-11 rebase below, because it
was designed before that subcommand-restructuring plan existed and
conflicted with it — the pattern this section describes is still the
right target, but whoever builds it next should design it together with
`cli-subcommands.md`, not bolt it onto the single-command `Main.kt` again.

Within that eventual dispatcher, **every subcommand should be
pipeline-invokable uniformly — there should be no "this subcommand
supports pipeline mode, that one doesn't."** A subcommand's logic is one
handler, callable either single-shot (`:cli some-command --arg ...`, for
direct human/ad hoc use) or via a pipeline request naming it — both paths
go through the same handler. `--word` / `--interactive` stay
per-subcommand (simple, direct, human-facing, no routing needed);
`--pipeline` is meant to be the one shared, multi-subcommand path.

**Worked example — the GBDT decomposition re-ranker.**
`data/grammar/fst/reranker_gbdt.py` began, and still lives, as a
pure-stdlib Python model, trained and validated entirely in Python (see
`data/grammar/fst/reranker-experiment.md`). It is already flagged, in
`doc/dev/plans/offline-dictionary-generation.md`, as due for a Kotlin port
into `:core`, with a committed per-word snapshot and regression gate. Once
that lands, the natural next step is to also expose it as a
`:cli --pipeline` command — hand it words, get back ranked decompositions
— so that Python work still needing a re-ranked list (a future spike, or
any later analysis) calls the Kotlin implementation as a subprocess
instead of re-scoring with the Python GBDT, or worse, keeping that Python
model alive indefinitely as a second, silently-drifting implementation.

In both (a) and (b): never end up with two maintained implementations of
the same logic, one in each language.
