# Plan: generate an offline dictionary

This would pre-compute most of the information we show on the Word Lookup screen
for the 10k most frequent words in the Hansard or gov.nu.ca.

This would allow us to invoke a LLM once and only once for each of those words.

The LLM would be used to do two things:
- Propose some possible meanings, in cases where we haven't found a definition 
  in any dictionary.
- Identify which of the decompositions generated by the analyser, seem to 
  correspond to an actual usage of the word found in the Hansard or gov.nu.ca
  A decomp can be grammatically correct, while still not be idiomatic. In other
  words, just because a decomp is grammatically correct, it doesn't mean that 
  it is likely to used in that way in real life.

## Goal

Primary consumers:

- Word Dictionary. Here, the goal is to avoid calling Guess Meaning on the fly.
  Many users may not have a Claude API key or know how to generatre it.  By 
  pre-compiling the guessed meaning offline, all users benefit from the Guess 
  Meaning feature.

- Morphem Dictioanry. Here, the goal is help with the **"good example words"** 
feature, whose design is in
[`../../morpheme-dictionary-examples-design.md`](../../morpheme-dictionary-examples-design.md). We want to make sure that the word examples we provide, correspond to 
an idiomatic decomp that contain the morpheme of interest. 


## Background — the problem this solves for the Morphem Dictionary

A "good example" of morpheme **M** is a word whose decomposition contains
M. The risk: the analyzer emits a decomposition containing M that is not
what is actually going on in the word, so the example misleads a learner.

Two facts narrow the problem:

1. **Benoît Farley (R2L's author): every decomposition R2L produces is
   grammatically valid.** R2L is lexicon + morphotactic adjacency +
   morphophonology, not a statistical segmenter — it does not emit
   garbage parses. This removes the worst case: an example word with *no*
   legitimate reading containing M.

2. **Benoît cannot vouch that every grammatically valid decomposition
   corresponds to a plausible idiomatic usage.** A word form can have
   several valid analyses; in real use one is meant. And a productive,
   agglutinative grammar *licenses* segmentations a linguist would still
   call wrong for a particular word (a root whose final syllable is
   homophonous with a suffix; a promiscuous affix the morphotactics let
   attach almost anywhere).

So what we want is: **a word that has an idiomatic decomposition
containing M** — "idiomatic" meaning: matched against real bilingual
sentence pairs.

## Rights: third-party dictionaries

This pipeline is **deliberately designed to need no new dictionary
licences.** Copyright protects the *expression* of a definition, not the
facts of which words exist or which morphemes a word contains. The design
relies only on:

- **Spalding** — rights already cleared, embedded in the app.
- **Tusaalanga** — a live third-party service under its own terms; we
  query it, we don't redistribute it.
- **LLM-generated senses** — the fallback for the (large) set of words no
  cleared dictionary covers.

The recovered **Living Dictionary** and any other unlicensed dictionary
(e.g. Dorais) are **not inputs to this pipeline** — not as content, and
not as a validation yardstick. Fair dealing (Canada) is a closed list of
purposes; "build a validation set / feed a scoring step" fits none of
them cleanly, and the rights holders here are a government Alain has an
ongoing relationship with. The clean uses of the recovered data
(extraction for the Bureau, informing Alain's own linguistic judgement,
aggregate coverage/frequency analysis, the Schneider subset if Benoît's
licence covers it) stay outside this plan.

## Pipeline (offline, at generation time)

For each of the top **N** Hansard word forms `W` (start N = 10 000):

1. **Decompose.** R2L on `W`; keep the top 5 decompositions in
   **re-ranker order**. (R2L, not FST: Benoît's grammaticality claim is
   about R2L; the FST is mid gold-fitting cleanup and emits ≈ 2× more
   decomps per word, i.e. more licensed-but-spurious noise. The examples
   design reached the same conclusion in its open-item 6.)

2. **Structural pre-filter.** `W` is a candidate example for morpheme `M`
   only if:
   - `M` appears in the re-ranker's **top-1 or top-2** decomposition, **and**
   - `n_decomps(W) ≤ 7` (ambiguity cap — a word with many analyses is
     where licensed-but-spurious M-attachment clusters; the examples
     design measured precision falling to ≈ 91 % for `n ∈ [8,10]`).

   This is free and deterministic. It removes the systematic-artifact
   category before any API call and shrinks the LLM workload.

3. **Dictionary lookup.** Find an entry for `W`, or for its **longest
   prefix**, in **Spalding** (already embedded, rights cleared for the
   app) and **Tusaalanga** (queried live, their service). Record source,
   whether the match was exact or prefix, and the matched form. (Prefix
   fallback is only meaningful for the *sense-guessing* side output; for
   example eligibility we require exact-word evidence, see step 4.)

   Recovered Living Dictionary word lists are **not** used here by default
   — see "Rights: third-party dictionaries" below. They would only be a
   minor tiebreaker ("is `W` a headword a learner would look up" vs. an
   inflected form), and Hansard top-10k membership is already an
   attestation.

4. **Corpus evidence.** Gather the bilingual Hansard sentence pairs that
   contain **`W` exactly** (not a prefix). Target 3–5 pairs; require ≥ 2.
   Because we mine the *most frequent* forms, exact-word pairs are
   effectively guaranteed for the top-10k.

5. **Build the LLM prompt.** Include:
   - `W` in Roman and syllabics;
   - the 5 decompositions, each rendered **with per-morpheme glosses and a
     plain-language paraphrase of the whole word** (glosses come from the
     Morpheme Dictionary pass-1 data / Benoît's morpheme DB). This turns
     the LLM's task from "do Inuktitut morphology" into "does this
     paraphrase match the English side" — a translation-checking task it
     is good at;
   - the sentence pairs (Inuktitut + English);
   - the dictionary entry if one was found.

6. **Ask Claude, per decomposition** (not "pick one"):
   ```
   for each of the 5 decompositions:
     { matches_usage: "yes" | "no" | "uncertain",
       confidence:    0.0 – 1.0,
       english_span:  "<the exact English words W corresponds to in the pair>",
       per_pair:      [ { pair_id, matches: bool, english_span } , ... ] }
   ```
   Requiring a **quoted English span per pair** forces real word
   alignment instead of hand-waving and gives something to spot-check.

   If no dictionary entry was found, also request
   `candidate_senses: [ { gloss, confidence } ]` — the sense-guessing side
   output. Not on the examples critical path.

7. **Resolve `usage_attested` per decomposition.** A decomposition `D` is
   marked `usage_attested = "yes"` iff:
   - Claude's `matches_usage == "yes"` with `confidence ≥ τ` (start
     `τ = 0.75`), **and**
   - it is supported by **≥ 2 sentence pairs**, *or* by 1 pair at
     `confidence ≥ 0.90`.
   Otherwise `"no"` or `"uncertain"` (e.g. 0 pairs, or model unsure).

8. **Emit the annotated record** (schema below).

Operational: one Claude call per word (batch a few words per call if the
context budget allows), one-time at generation, strong model
(accuracy-critical), shared instructions prompt-cached. Store the **raw
model verdicts keyed by word** so regeneration is incremental and
auditable. Home: a `:cli` subcommand (e.g. `--build-offline-dictionary`)
or a script under `data/grammar/fst/` beside the other generation
scripts; committed output is the JSONL plus generated Kotlin.

## The artifact

### Per-word record (`offline-dictionary.jsonl`, committed generation intermediate)

```jsonc
{
  "word": "tusalauqtuq",
  "word_syllabic": "ᑐᓴᓚᐅᖅᑐᖅ",
  "hansard_rank": 342,
  "hansard_freq": 118,
  "govnu_freq": 41,                    // null if absent from the gov.nu.ca crawl
  "dict_entry": {                      // null if none found
    "source": "spalding",
    "match": "exact",                  // "exact" | "prefix"
    "matched_form": "tusaq"
  },
  "decomps": [
    {
      "rank": 1,                       // re-ranker rank among W's decompositions
      "morphemes": ["tusaq/1v", "lauq/1vv", "juq/1vn"],
      "gloss":     ["hear", "PAST", "3sg.IND"],
      "paraphrase_en": "he/she heard",
      "usage_attested": {
        "verdict": "yes",              // "yes" | "no" | "uncertain"
        "confidence": 0.92,
        "corpus": "hansard",
        "pairs_supporting": 3,
        "pairs_examined": 4,
        "evidence": [
          { "iu": "…tusalauqtuq…", "en": "…we heard…", "en_span": "we heard" }
        ]
      }
    }
    // … up to 5
  ],
  "generated_senses": [                // present only when dict_entry == null
    { "gloss": "to hear (something)", "confidence": 0.8 }
  ],
  "model": "claude-…",
  "generated_at": "2026-09-06T…Z"
}
```

Key point — **how the dictionary specifies which decompositions match
corpus usage**: every decomposition carries a `usage_attested` block, not
a bare flag. It states a `verdict` (`yes` / `no` / `uncertain`), a
`confidence`, **which corpus** the evidence came from (always `hansard` —
gov.nu.ca never supplies sentence evidence), how many sentence pairs
supported vs. were examined, and the sentence pairs themselves with the
aligning English span quoted. A downstream consumer can therefore re-apply
its own threshold instead of trusting ours.

### Shipped, inverted artifact (consumed by pass 2)

`morphemeId → [ { word, score, evidence_strength }, … ]`, pre-scored,
root-balanced, capped at 20 — **exactly the encoding and machinery already
specified in `morpheme-dictionary-examples-design.md`**, with only the
eligibility gate changed:

> **W is eligible as an example of M** iff some decomposition `D` of `W`
> has `M ∈ D` **and** `D.usage_attested.verdict == "yes"` **and** `D` is
> within the re-ranker top-2 **and** `n_decomps(W) ≤ 7`.

Scoring (fitness, `rootHasDefinition`, normalised frequency, cleaner
decomposition), root balancing (`ExamplesRootsBalancer` + its test), and
the cap-20 truncation are unchanged from that document. `evidence_strength`
(pairs_supporting, confidence) becomes an additional tie-break, ranked
below fitness and above raw frequency.

Optional second tier, de-emphasised in the UI: decompositions with
`verdict == "uncertain"` but `M` in the re-ranker top-1 — shown only when
a morpheme has too few `"yes"` examples.

## Validation — do this before trusting the judge

Run the full pipeline on the **922 `--fair` gold words** and compare
Claude's `usage_attested` verdicts against the gold's Hansard-attested
decomposition.

Metrics:

- **Morpheme-level precision** — of the decompositions Claude marks
  `"yes"`, what fraction contain the gold-relevant morphemes for that
  word. This (not whole-decomposition precision) is the real target: an
  example only needs *M* to be genuinely present. Per the examples
  design's open-item 3, morpheme-level precision should exceed the P@k
  figures.
- **Recall** — does the gold decomposition itself get a `"yes"`.
- **Lift over the re-ranker alone** — compare against simply taking the
  re-ranker top-1 with no LLM step. Quantify what the API cost buys.

**Ship criterion:** morpheme-level precision ≥ ~95 % on the `"yes"` set.
If lower: raise `τ`, require more supporting pairs, or keep the strict
"M in every decomposition" structural floor from the examples design as an
additional AND-condition.

## Open decisions

- `τ` and the minimum-pairs rule — set empirically from the gold
  validation, not guessed.
- Batch size per Claude call.
- Keep `"uncertain"` decompositions in the per-word record for later
  re-processing (recommended: yes, storage is cheap).
- Also emit a single `best_decomp` per word (highest-confidence `"yes"`,
  else re-ranker top-1) for non-examples consumers.
- N = 10 000 vs. larger. The examples design shows a larger mined corpus
  is the main coverage lever, but every added word is now an API call, so
  cost scales linearly. Start at 10 000; expand only if coverage against
  `LinguisticData.allMorphemeIDs()` (5211) is disappointing.

## Non-goals

- Not a runtime feature — the shipped artifact is frozen in the APK; no
  live corpus queries, no live LLM calls.
- Not rebuilding Guess Meaning.
- Not using the recovered Living Dictionary (or Dorais, or any unlicensed
  dictionary) as pipeline input — content or validation (see "Rights").
- Not sending gov.nu.ca content to the LLM (frequency counts only).
- Not the gov.nu.ca live crawl (blocked; tracked separately in
  `gov-nu-ca-crawling-investigation.md`).
